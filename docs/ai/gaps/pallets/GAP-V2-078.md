# GAP-V2-078 — Código GS1-128 de caja usa el AI de precisión incorrecto (3100/3200 en vez de 3102/3202)

## Problema

`getGs1128` y `getGs1128WithPounds` (`src/hooks/pallets/usePalletBoxOperations.ts:73-88`) generan
el código GS1-128 de cada caja siempre con el Application Identifier literal `3100` (kg) o `3200`
(libras), pero codifican el peso con 2 decimales implícitos:

```ts
// usePalletBoxOperations.ts:73-78
const getGs1128 = (productId, lot, netWeight) => {
  const boxGtin = getBoxGtinById(productId);
  const weight = parseFloat(String(netWeight)) || 0;
  const formattedNetWeight = weight.toFixed(2).replace('.', '').padStart(6, '0');
  return `(01)${boxGtin}(3100)${formattedNetWeight}(10)${lot}`;
};
```

Según el estándar GS1 General Specifications, la familia de AIs `310n` (peso neto en kg) codifica
en el propio dígito `n` cuántos decimales tiene el valor: `3100` = 0 decimales (kg enteros),
`3101` = 1 decimal, **`3102` = 2 decimales**. Este código usa siempre `3100`/`3200` (0 decimales)
mientras codifica el valor asumiendo 2 decimales. Ejemplo real: una caja de 12,34 kg produce
`(01)<gtin>(3100)001234(10)<lote>`. Cualquier lector GS1-128 estándar (el de un cliente,
distribuidor, transportista o carretilla elevadora en un almacén externo) decodificará ese valor
como **1234 kg** — 100 veces el peso real — porque interpreta `3100` literalmente como "sin
decimales".

El código se imprime como un barcode físico real: `src/lib/barcodes.js` mapea `'gs1-128' →
'CODE128'` y `serializeBarcode` reenvía la cadena "intacta" para su renderizado. El propio parser
del proyecto (`parseGs1128Line` / `normalizeScannedCodeToGs1128` en `src/lib/gs1128Parser.js:19-31,
48-76`) siempre divide por 100 al leer, así que el error es invisible en el circuito interno
(crear caja → reimprimir → volver a escanear con la propia app), pero rompe la interoperabilidad
con cualquier sistema externo que decodifique GS1-128 según el estándar real — que es precisamente
el propósito de usar GS1-128 en vez de un código propietario.

`src/lib/gs1128Parser.js:1-6` documenta explícitamente que este parser está "Unificado para
Autoventa (Step2QRScan) y editor de palets (usePallet)" — el mismo error de AI se propaga a
cualquier flujo que reutilice este parser fuera del alcance de esta auditoría (pallets).

## Objetivo

El código GS1-128 generado (e impreso) para cada caja usa el Application Identifier correcto para
la precisión decimal realmente codificada, de forma que cualquier lector GS1-128 estándar externo
decodifique el peso neto real (no 100 veces más).

## Contexto

Este bug es de alto impacto porque el vector de exposición es un código de barras físico impreso
y compartido con terceros (clientes, transportistas), no solo un dato interno. La corrección debe
hacerse en el generador (`usePalletBoxOperations.ts`) y en el parser compartido
(`gs1128Parser.js`) a la vez, porque ambos deben coincidir en el mismo AI o el propio sistema
dejará de poder reconocer sus propios códigos ya emitidos/reimpresos. Al tocar
`gs1128Parser.js`, el fix beneficia automáticamente también a Autoventa (Step2QRScan), que ya
comparte el mismo archivo — pero esa superficie no forma parte de esta auditoría y debe
verificarse por separado antes de cerrar el GAP (ver Plan de validación).

## Solución propuesta

- Cambiar el AI emitido de `3100`/`3200` a `3102`/`3202` (2 decimales) en `getGs1128` y
  `getGs1128WithPounds` (`usePalletBoxOperations.ts:73-88`), manteniendo el mismo formato de
  6 dígitos ya usado (`toFixed(2).replace('.', '').padStart(6, '0')` sigue siendo válido para AI
  con 2 decimales).
- Actualizar `parseGs1128Line` y `normalizeScannedCodeToGs1128` (`gs1128Parser.js`) para
  reconocer `3102`/`3202` como los AIs válidos (además de, temporalmente, seguir aceptando
  `3100`/`3200` en lectura para no romper códigos ya impresos/existentes en cajas activas —
  decisión a confirmar con Jose, ver pregunta abajo).
- Revisar si hay códigos ya generados y almacenados en backend con el AI incorrecto que deban
  migrarse o seguir siendo legibles en modo de compatibilidad.

## Criterios de aceptación

- [x] `getGs1128`/`getGs1128WithPounds` emiten AI `3102`/`3202` para el peso codificado con 2
      decimales.
- [x] `parseGs1128Line`/`normalizeScannedCodeToGs1128` reconocen el nuevo AI correctamente y
      decodifican el peso neto real (no x100).
- [x] Un código generado por el propio sistema, decodificado manualmente aplicando la regla GS1
      estándar para el AI emitido, produce el mismo peso neto mostrado en la UI.
- [x] Se documenta explícitamente (comentario en ambos archivos) el AI usado y por qué, para
      evitar que un futuro cambio de precisión (p.ej. pasar a 3 decimales) reintroduzca el mismo
      desajuste.

## Resultado

`getGs1128`/`getGs1128WithPounds` (`usePalletBoxOperations.ts`) cambian AI
`3100`/`3200` → `3102`/`3202`, con comentario explicando la familia `310n`/`320n`
y por qué no usar 0 decimales. `parseGs1128Line`/`normalizeScannedCodeToGs1128`
(`gs1128Parser.js`) reconocen ahora `3102`/`3202` como AI primario y siguen
aceptando en lectura el AI legacy `3100`/`3200` (decodifican igual, `/100`,
porque el empaquetado numérico nunca cambió — solo el AI declarado estaba mal
etiquetado); `normalizeScannedCodeToGs1128` re-normaliza códigos legacy al AI
correcto. Verificación empírica con `node` (no hay backend disponible en este
entorno, pero el parser es puro JS/testeable directamente):

- Generación: 12.34 kg → `(3102)001234` (correcto, AI de 2 decimales).
- Decodificación AI nuevo: `(3102)001234` → 12.34 kg.
- Decodificación AI legacy (códigos ya impresos): `(3100)001234` → 12.34 kg
  (compatibilidad retroactiva preservada).
- Libras: `(3202)001234` → 5.6 kg (12.34 lb × 0.453592, redondeado).
- `normalizeScannedCodeToGs1128` sobre un código legacy devuelve la forma
  canónica con AI `3102`.

Fuera de alcance (confirmado, no tocado): `useProductionInputsManager.js`,
`ProductionInputsAddDialog.jsx`, `LabelSelectorSheet.jsx` — mismo bug de AI en
otro módulo (Producciones/Etiquetas), explícitamente fuera de esta auditoría de
`pallets` según el propio GAP. `npm run type-check` y `npm run lint` limpios.

## Resultado de auditoría

### Veredicto: done

Verificado empíricamente con Node (`parseGs1128Line`/`normalizeScannedCodeToGs1128`
importados directamente, sin mocks) sobre el código real de barras sin paréntesis
(formato de escaneo real, FNC1): AI nuevo `3102`/`3202` y AI legacy `3100`/`3200`
decodifican ambos a 12.34 kg para un peso codificado `001234` — confirma que el
cambio de AI es puramente semántico (declara correctamente los 2 decimales que ya
se codificaban) y no rompe la compatibilidad retroactiva con cajas ya impresas.
Conversión libras→kg (`× 0.453592`) intacta: `3202` con `001234` → 5.6 kg
(12.34 lb × 0.453592, redondeado a 2 decimales), igual que documentaba el GAP.
`normalizeScannedCodeToGs1128` re-normaliza un código legacy (`3100`/`3200`) a la
forma canónica con AI `3102`/`3202`, correcto.
