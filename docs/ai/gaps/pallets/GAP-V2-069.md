# GAP-V2-069 — "Deshacer" cambios (desktop) no confirma, a diferencia de "Descartar" en mobile

## Problema

El botón "Deshacer" del pie de página de `PalletView` (desktop) llama a
`resetAllChanges()` directamente, sin confirmación:

```tsx
// src/components/Admin/Pallets/PalletDialog/PalletView/index.tsx:2755-2761
<Button
  variant="outline"
  onClick={handleOnClickReset}
  disabled={saving || isReadOnly || !hasPalletChanges}
>
  Deshacer
</Button>
```

```tsx
// handleOnClickReset, línea 443-446
const handleOnClickReset = () => {
  if (isReadOnly) return;
  resetAllChanges();
};
```

El equivalente mobile de la misma acción ("Descartar") sí exige confirmación explícita, con
copy que además avisa cuántas cajas se perderían:

```tsx
// src/components/Admin/Pallets/PalletDialog/MobilePalletView/index.tsx:385-424
<Button variant="outline" size="lg" className="flex-1"
  onClick={() => setDiscardDialogOpen(true)} disabled={saving}>
  <RotateCcw /> Descartar
</Button>
...
<AlertDialog open={discardDialogOpen} onOpenChange={setDiscardDialogOpen}>
  <AlertDialogContent>
    <AlertDialogHeader>
      <AlertDialogTitle>¿Descartar los cambios?</AlertDialogTitle>
      <AlertDialogDescription>
        {boxes.length > 0
          ? `Se perderán todos los cambios, incluyendo las ${boxes.length} caja${boxes.length !== 1 ? 's' : ''} del palet. Esta acción no se puede deshacer.`
          : 'Se perderán todos los cambios realizados en este palet.'}
      </AlertDialogDescription>
    </AlertDialogHeader>
    ...
```

`resetAllChanges()` can discard a non-trivial amount of unsaved work (added boxes, edited
weights/lots, tare, observations, order link) with a single accidental click on desktop,
while the mobile flow protects the same action. This is a direct mobile/desktop UX
divergence for a data-loss-risk action.

## Objetivo

El botón "Deshacer" en desktop exige la misma confirmación explícita que "Descartar" en
mobile antes de perder cambios sin guardar, con mensaje equivalente sobre el número de
cajas afectadas.

## Contexto

Es la misma función `resetAllChanges()` invocada desde ambas superficies (`usePallet`),
solo difiere el nivel de protección de UI alrededor de la llamada. Ver también GAP-V2-068
para el otro caso de confirmación ausente en el mismo archivo.

## Solución propuesta

Añadir un `AlertDialog` de confirmación para "Deshacer" en `PalletView` (desktop),
replicando el copy y la lógica de conteo de cajas ya implementada en
`MobilePalletView/index.tsx` (`¿Descartar los cambios?` / mensaje condicional según
`temporalPallet.boxes.length`).

## Criterios de aceptación

- [ ] El botón "Deshacer" en desktop abre un `AlertDialog` antes de ejecutar
      `resetAllChanges()`.
- [ ] El mensaje de confirmación indica cuántas cajas se perderían, con el mismo criterio
      condicional usado en mobile (mensaje distinto si `boxes.length > 0` vs `0`).
- [ ] `disabled={saving || isReadOnly || !hasPalletChanges}` se mantiene en el botón que
      abre el diálogo.
- [ ] No se modifica el comportamiento de "Guardar" ni de otros botones del footer.

## Plan de validación

```text
npm run type-check
npm run lint
Verificación manual: en desktop, editar un palet (añadir una caja o cambiar tara) → clic en
"Deshacer" → confirmar que aparece el AlertDialog con el conteo correcto de cajas → cancelar
no debe alterar el estado; confirmar sí debe revertir los cambios.
```

## Notas de implementación

**Normalización (gap-normalizer, 2026-07-05):** marcado `ready`, sin cambios de
fondo. Independiente de GAP-V2-068 (misma archivo, distinto botón/acción) — se

## Resultado

Añadido `AlertDialog` de confirmación para "Deshacer" en `PalletView/index.tsx`,
replicando copy y lógica condicional de conteo de cajas de
`MobilePalletView/index.tsx` (`¿Descartar los cambios?`). El botón abre el
diálogo (`setResetConfirmOpen(true)`) en vez de llamar a `resetAllChanges()`
directamente; la ejecución real ocurre en `handleConfirmReset`. Se mantiene
`disabled={saving || isReadOnly || !hasPalletChanges}` en el botón que abre el
diálogo. `npm run type-check` y `npm run lint` limpios.

**Corrección tras primera pasada de gap-auditor:** mismo problema que
GAP-V2-068 — `temporalPallet?.numberOfBoxes` corregido a
`temporalPallet?.boxes?.length` para reflejar el total real de cajas que se
perderían al descartar cambios (`resetAllChanges()` opera sobre el array
completo, no solo las disponibles).

**Corrección tras ux-reviewer:** el título del diálogo decía "¿Descartar los
cambios?" (copiado literalmente de mobile) mientras el botón que lo abre y la
acción de confirmar dicen "Deshacer" — mezcla de verbos en el mismo flujo.
Unificado a "¿Deshacer los cambios?" para alinear con el resto del flujo.

FLOW SIMULATION

Role: usuario editando un palet (añade una caja o cambia la tara), no read-only.
Entry point: PalletDialog (desktop) → footer del editor de palet.

Step 1: Usuario hace un cambio (p. ej. añade una caja). El botón "Deshacer" del footer pasa de
        deshabilitado a habilitado (`!hasPalletChanges` dejó de bloquearlo).
  → Action: clic en "Deshacer".
  → Result: se abre `AlertDialog` — título "¿Descartar los cambios?", descripción condicional
    (menciona el número de cajas si `boxes.length > 0`, mensaje genérico si no hay cajas).
  → Potential friction: el botón que dispara el diálogo dice "Deshacer", pero el título del
    diálogo dice "¿Descartar los cambios?" y ninguno de los dos coincide del todo con el texto
    del botón de acción dentro del diálogo, que vuelve a decir "Deshacer". Es una mezcla de dos
    verbos ("Deshacer" / "Descartar") para la misma acción dentro del mismo flujo de 3 clics.
    En mobile los tres puntos (disparador, título, acción) usan siempre "Descartar" —
    coherencia total. En desktop la coherencia se rompe porque el botón del footer ya se
    llamaba "Deshacer" antes de este GAP y no estaba en el criterio de aceptación renombrarlo,
    así que el título de diálogo (copiado literalmente de mobile) queda desalineado con el
    verbo del botón que lo abre.

Step 2: Usuario pulsa "Cancelar".
  → Action: `AlertDialogCancel` cierra el diálogo.
  → Result: `resetConfirmOpen` vuelve a `false`, ningún cambio se pierde, estado intacto.
  → Potential friction: ninguna.

Step 3: Usuario reabre el diálogo y pulsa "Deshacer" (acción del `AlertDialogAction`).
  → Action: `handleConfirmReset` → `resetAllChanges()` + cierre del diálogo.
  → Result: `temporalPallet` vuelve al estado guardado (`{ ...pallet }`), toast de éxito
    ("Cambios desechados"). El botón "Deshacer" del footer vuelve a deshabilitarse porque
    `hasPalletChanges` pasa a `false`.
  → Potential friction: ninguna en el resultado funcional — el usuario obtiene exactamente lo
    esperado, solo la etiqueta verbal del recorrido es inconsistente (ver Step 1).

Edge cases simulated:
  → Empty state (sin cambios pendientes): el botón "Deshacer" ya estaba deshabilitado por
    `!hasPalletChanges` antes de este GAP y se mantiene — no es posible abrir el diálogo sin
    haber hecho ningún cambio. Mejor cubierto que el caso equivalente de GAP-V2-068 (que sí
    permite abrir el diálogo con 0 cajas).
  → Permission edge (isReadOnly): el botón permanece deshabilitado, sin cambios respecto al
    original.
  → Partial data (cambios que no son de cajas, p. ej. solo se editó la tara u observaciones sin
    tocar el array de cajas): si el palet tiene cajas, la descripción dirá "Se perderán todos
    los cambios, incluyendo las N cajas del palet", aunque las cajas en sí no hayan cambiado.
    Puede sonar más alarmante de lo necesario, pero es el mismo copy ya validado y usado en
    `MobilePalletView` — replicarlo aquí es lo que pedía explícitamente el GAP, no es una
    regresión ni una desviación introducida por esta implementación.
  → Concurrent action: no aplica — operación 100% client-side sobre `temporalPallet`, sin
    llamada a API en este paso.
  → Mobile: fuera de scope — ya tenía el patrón correcto ("Descartar" en las 3 superficies),
