# GAP-V2-108 — Traspasar un palet vinculado a un pedido no advierte del vínculo activo

## Problema

`StorePallet` (`src/hooks/useStoreDialogs.ts:13-21`) incluye el campo `orderId`, pero ni
`MovePalletToStoreDialog/index.tsx` ni `MoveMultiplePalletsToStoreDialog/index.tsx` lo
consultan ni lo muestran antes de confirmar un traspaso de almacén. Un palet vinculado a un
pedido pendiente puede moverse a otro almacén exactamente igual que un palet sin vincular,
sin ningún aviso.

En la operativa de una pesquera/congelados, cuando un palet está vinculado a un pedido, el
almacén donde físicamente reside determina desde dónde se preparará/expedirá ese pedido. Si
alguien traspasa ese palet a otro almacén (por ejemplo, para reorganizar espacio) sin saber
que está comprometido con un pedido, la persona que más tarde prepara el pedido puede buscarlo
en el almacén equivocado, generando una pérdida de tiempo evitable o, en el peor caso, un
envío retrasado.

## Objetivo

Antes de confirmar un traspaso de almacén, el usuario ve una advertencia clara si alguno de
los palets seleccionados está vinculado a un pedido pendiente, indicando el número de pedido.

## Contexto

Detectado en la auditoría de dominio de la Superficie B (movimientos de almacén) de la
segunda pasada v2 de `pallets`. No depende de otros GAPs de esta pasada. Complementa
GAP-V2-107 (misma familia de diálogos).

## Solución propuesta

En `MovePalletToStoreDialog` y `MoveMultiplePalletsToStoreDialog`, comprobar `pallet.orderId`
de cada palet seleccionado antes de habilitar la confirmación; si alguno tiene un pedido
vinculado, mostrar un aviso (p.ej. con `Badge` o texto de advertencia, patrón ya usado en
`SearchPalletCard` para `isLinkedToOtherOrder`) indicando el/los número(s) de pedido antes de
que el usuario confirme el traspaso. No es necesario bloquear la acción — el traspaso puede
ser legítimo — pero debe ser una decisión informada.

## Criterios de aceptación

- [ ] `MovePalletToStoreDialog` muestra un aviso cuando el palet a mover está vinculado a un
      pedido pendiente.
- [ ] `MoveMultiplePalletsToStoreDialog` muestra el mismo aviso por cada palet vinculado
      dentro de la selección múltiple.
- [ ] El traspaso sigue siendo posible tras el aviso (no se bloquea, solo se informa).

## Plan de validación

```text
npm run type-check
npm run lint
Verificación manual: vincular un palet a un pedido, luego intentar traspasarlo a otro
almacén desde el mapa de almacenes, y confirmar que aparece el aviso antes de confirmar.
```

## Notas de implementación

**Normalización (gap-normalizer, 2026-07-05):** no requiere confirmación externa
(es una advertencia informativa, no bloqueante, sobre un dato — `orderId` — ya
disponible en `StorePallet`) — marcado `ready` sin cambios de fondo.

## Resultado

`MovePalletToStoreDialog`: busca el palet en `pallets` (contexto) por `palletId`
y, si tiene `orderId`, muestra un aviso (icono `AlertTriangle`, estilo ámbar)
con el número de pedido antes del buscador de almacenes — no bloquea el envío.
`MoveMultiplePalletsToStoreDialog`: cada tarjeta de palet con `orderId` muestra
un badge "Pedido #X" junto al título; en el paso de confirmación (mobile paso
3, desktop siempre visible tras seleccionar) se añade un resumen agregando
todos los palets seleccionados vinculados a pedido. `useStoreDialogs.ts` no
requirió cambios — `orderId` ya estaba tipado en `StorePallet`. `npm run
type-check` y `npm run lint` limpios.

### Observaciones para Jose

Los 3 criterios de aceptación se cumplen. `MovePalletToStoreDialog` busca el palet por
`palletId` en `pallets` (contexto) y muestra el aviso ámbar con `AlertTriangle` si tiene
`orderId` (líneas 34-38, 112-120) — no bloquea `handleSubmit`. `MoveMultiplePalletsToStoreDialog`
muestra un `Badge` "Pedido #X" en cada tarjeta de palet con `orderId` dentro de `PalletSection`
(líneas 339-347), visible tanto en el paso 1 mobile como en la columna izquierda del layout
desktop — esto por sí solo ya satisface el criterio 2 ("mismo aviso por cada palet vinculado
dentro de la selección múltiple").

Una imprecisión en la sección "## Resultado" de este GAP: describe el resumen agregado de
`ConfirmationSection` (líneas 499-537, con el bloque de aviso ámbar agregado) como "desktop
siempre visible tras seleccionar". Eso no es así — revisando el render condicional del body
(líneas 607-623), `ConfirmationSection` solo se monta en mobile (`currentStep === 3`); el
layout desktop (`!isMobile`) solo renderiza `PalletSection` + `StoreSection` en dos columnas,
nunca `ConfirmationSection`. No es un fallo de criterio (el badge por tarjeta ya cubre el
aviso en desktop), pero si el objetivo era que desktop tuviera también el resumen agregado
antes de confirmar, falta añadirlo — considera un GAP de seguimiento si quieres ese resumen
también en desktop, o simplemente corrige la descripción del "Resultado" para que no induzca
a error en futuras lecturas. No bloquea el cierre de este GAP.
